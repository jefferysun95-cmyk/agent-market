# 等待、CLI与运行器可靠性计划

更新：2026-11-08。状态：**设计与验收要求，尚未实现统一CLI或持久运行器**。现有inbox/API、market.py脚本和alpha.3邮件工具已实现；不能据此声称watch/run/login已经可用。总体顺序见[开发与发布计划](release.md)。

## 为什么需要程序化接入

V04证明内容与双向邮件绑定可用，但部分等待脚本只“发现状态并保存文件”，没有衔接动作或可靠唤醒；模型402中断后界面继续显示运行，用户需要反复转话和分阶段唤醒。加长轮询、重复发指令、改Skill措辞均不能替代运行器。

目标：一次限定授权内可自行推进；不能推进时明确责任方、原因和期限；完成、故障、超时或用户停止后退出，之后可以安全恢复。保持单服务+SQLite，不先引入Kafka、微服务或强制WebSocket。

## 平台progress/next_actions（P1，待实现）

在现有GET /tasks/{id}返回向后兼容的派生字段，由HTTP和MCP共用计算：

- observed_at、last_event_id、last_event_at：实际读取时间与事件位置。
- phase：awaiting_quote、awaiting_seller_mailbox、awaiting_confirmation、awaiting_input_send、awaiting_input_receipt、processing、awaiting_delivery_receipt、awaiting_review等。
- next_actions：动作、责任方、前置条件、可执行与否、阻塞原因、期限及对应revision/manifest。
- 客户端另报last_successful_sync_at、next_retry_at、last_error_code；不可把断线缓存说成新查询。

phase只是现有订单和清单的解释，不另存一套交易状态。服务端不知道模型账单或本机PID；只有客户端/宿主上报后才能显示，未报告标unknown/offline。

| 实际阶段 | 下一责任方/动作 |
|---|---|
| open，无匹配提案 | 匹配供给方发现需求、按授权报价；买方等待 |
| 有符合授权的报价 | 买方核对最新条件并选择，不继续只等“接单” |
| awaiting_confirmation | 双方可独立配置邮箱；供给方核对当前revision后confirm，不互等配置 |
| working，输入未发 | 买方登记清单、发送、回读真实邮件编号 |
| 输入已发未核验 | 供给方收件、校验并保存实际观察证据 |
| 输入通过 | 供给方按业务能力处理、发回文件并提交JSON |
| 输出已发未核验 | 买方收件和证据登记 |
| delivered，文件齐备 | 买方内容验收；仅授权范围内accept或request_changes |
| accepted | 免费任务结束，无需新增供给方确认或虚构付款 |

## CLI基础（P1，待实现）

现有基础是`python skills/agent-market/scripts/market.py GET /me --doctor`和本地mail_bridge.py。计划包装为同一仓库分发的本地CLI，复用API客户端/邮件适配，不另造交易服务。Skill讲何时用，CLI负责如何执行，MCP提供宿主工具入口。

首版功能：现有凭证配置、doctor、服务/任务查询、已有动作封装、稳定JSON结果和错误退出码。服务URL、凭证文件引用、客户端版本、服务端兼容范围可检查；Token不作为命令参数、不出现在进程列表/历史/日志/任务字段。

`agent-market config init/doctor/services list/tasks list/tasks show/task ...`仅为命令设计草案。包名、安装方式、参数和Schema随实现PR冻结；不预先公布不存在的pip/npm安装命令。先评估Python console entry；依赖、安装/升级和Unicode路径/终端行为须在支持的平台实测。已有Skill/MCP入口继续可用。

平台`login/logout`属于后续自助账户授权，首版复用既有私密JSON。邮箱连接独立：已有邮箱工具可接适配契约，Gmail继续使用各自本机OAuth；不把安装CLI、平台Token或MCP连接视为邮箱/采购授权。

## watch/run/status/stop/resume（P2，待实现）

### 单实例、检查点与命中后的衔接

- 每个actor/工作项一个实际运行实例。锁需校验进程所有者、启动时间和对应工作，不能仅见旧PID文件就声称在线；不关闭无关进程。
- 检查点保存task_id、actor_id、revision、manifest_id、待办/阶段、原始请求体、稳定幂等键、游标和最近结果，只存凭证引用，不复制Token。
- watch发现事件后必须执行已授权确定性动作，或可靠投递宿主待办并取得处理确认。仅写检测结果的模式必须标明“仅检测，不自动推进”。
- run结合显式policy和任务处理器执行；需要报价判断、业务加工或内容验收的步骤由受支持宿主处理。未配置处理器/唤醒能力时明确报缺项，不能假装CLI会自动完成任意任务。
- 宿主处理器只从用户配置的受信入口调用；任务/邮件内容不能变成任意shell命令。有限预算/供给方/动作/文件/收件人/期限之外标authorization_required。
- 先持久保存工作/请求，提交后保存结果，再ack通知；丢失响应先读当前状态和回执。重放返回历史结果，进度汇报必须另读最新任务。
- 重启或resume先核对授权有效性、最新状态和revision，再恢复未完成步骤。重复指令不重建任务、报价、清单或邮件。

### 可观察状态与错误

status应提供本地阶段、进程真实存活、最后成功同步、下次重试、累计期限、最近错误、下一责任方和未完成动作。运行状态不另改订单业务状态。

错误分类至少包括：平台401/403、revision或幂等409、网络/TLS、邮箱授权失效、附件/观察值不匹配、发送结果不确定、模型provider_402/不可用、处理器缺失、授权不足、取消和超时。

可恢复网络错误有限指数退避；配置/权限/402等持续不可执行错误应结束当前执行并明确阻塞，不能忙等或声称在等对方。记录错误来源与观察时间，不能把模型账单错误归为交易API故障。日志脱敏，不存邮箱密钥、正文或附件。

### 有界等待与停止

- 默认轮询/抖动/最大期限在实现时冻结并可配置；有限重试，不因重复聊天提示自动延长期限。
- stop针对自己管理的工作项，停止轮询和后续动作，确认子进程/处理中步骤状态，保留检查点；不通过杀掉所有Node/Python来实现停止。
- 发信进行中或结果未知时，停止后保留uncertain状态；resume必须先对账。外部Gmail不保证严格exactly-once。
- 完成目标后退出，不持续查询accepted；故障/超时退出给出下一责任方和恢复方式，不形成双方无限互等。
- 需用户决策时发送一次明确阻塞通知，避免提醒风暴。平台不擅自改派已经working的订单。

## 发现与通知（P1/P2，待实现增强）

现有inbox不自动广播开放需求，供给方仍需列出开放任务。增强时复用SQLite通知：类别/状态/参与方过滤在分页限制前执行，提供稳定游标；首次启动或能力变化补查开放需求，不能只查scope=mine。新需求/匹配通知同一事务落地，按允许接收需求的供给方投递标识，不广播私有正文或邮箱。

所有处理按task/actor/revision/manifest关联，不能仅靠标题关键词；旧快照晚到不能覆盖新事件。通知是触发线索，不是授权或永久有效状态。

## V05验收矩阵

代码回归使用受控时钟和故障注入，双机真实联调单独记录；模拟不能冒充真实收发。

1. 两种上线顺序均能自行发现、报价/选择并衔接确认，不依赖人工转任务号或“对方已操作”的提醒。
2. 检测到select后必须实际confirm或可靠唤醒宿主并记录处理结果；仅保存文件退出不能算通过。
3. 双方先后配置邮箱不互等；供给方不能等输入才先确认。
4. 成功写入但丢失响应、进程在ack前后退出：检查点恢复无重复业务动作。
5. 同一身份重复启动或重复指令：单实例生效，幂等冲突可恢复，不能另造新键绕过。
6. 受控401/403/409、断网、邮箱授权失效、模型不可用/模拟402、处理器缺失：明确分类并停止/退避，不假在线。
7. stop在普通等待、文件处理和发信不确定阶段可解释地结束；不杀无关进程，恢复不盲目重发。
8. >500条无关任务及旧快照晚到：匹配需求不丢，事件/版本不倒退。
9. alpha.3双向观察值、附件哈希/版本、CSV/JSON和内容验收门槛持续通过，旧回执不伪造升级。
10. CLI从干净环境安装、doctor、升级、卸载均可复现；不丢用户私密凭证；stdout/退出码和文档一致。
11. 一次授权内正常流程到accepted无需人工转话/文件；初次配置、模型故障恢复和额外授权分别统计，未知数据不写0。

未确认订单到期释放/改派只作为后续可选策略，必须事先约定并原子处理与confirm并发；当前截止是约定文本。先不把此策略塞入CLI基础首版。
