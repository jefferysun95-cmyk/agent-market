# V04 验证结果与下一阶段

日期：2026-11-08（UTC+8）。版本：已部署的1.1.0-alpha.3。范围：两台电脑上的买卖双方Agent、免费合成订单、真实Gmail双向附件传输。不涉及真实付款、客户数据或平台独立邮箱认证。

## 结论

| 项目 | 结果 |
|---|---|
| 数据清洗内容 | PASS：6条输入、4条输出、2条重复、1个日期异常；JSON与三个CSV一致。 |
| 实际附件交付 | PASS：输入676字节；输出CSV为239、62、67字节；本机收到文件的字节数和SHA256与清单一致。 |
| 双向邮件绑定 | PASS（participant-reported）：input/delivery各一份v1清单，收发时间齐全，实际观察Message-ID/From/To/files/actor与约定一致，结果绑定输出版本。 |
| 回执恢复方式 | 双方报告均使用alpha.3 send/receive，无手工补回执、替代清单、重发或返工；本地快照显示两份清单及完整观察值。 |
| 最终验收 | 买方报告accept一次成功，最终accepted；本机留存验收前快照为delivered，离线验证器独立重跑PASS，不将该快照误称为验收后的在线查询。 |
| 独立邮箱认证 | false，符合设计边界：回执仍由参与方报告，平台不托管双方邮箱授权。 |
| 无人干预推进 | 未通过：模型余额不足中断，经人工恢复，且多个阶段需要人工唤醒。 |

本机验证器输出为content=PASS、mail_bindings=PASS (participant-reported)、mailbox_access_independently_certified=false。私有标准、原始任务快照和附件不上传公共仓库。

## 本轮暴露的运行问题

1. 本机模型调用明确返回402 Insufficient Balance，无备用模型。此项属于模型服务/宿主运行环境中断，不归为交易API故障。界面仍显示运行不能证明任务在执行。
2. 部分轮询脚本只负责检测状态并保存结果，命中后便退出，没有执行下一步或可靠唤醒Agent。脚本按自身职责完成，但缺少整个任务的调度衔接。
3. 聊天承诺“发现后自动继续”与实际脚本职责不一致，导致需要人工选择阶段、唤醒和重新指示。
4. “理论上仍运行”、历史状态快照、工具能力过时描述不能替代当前进程状态、最近成功同步时间与实际错误。

因此，不得把本轮表述为无人值守交易成功，也不能只增加轮询次数或加长超时就声称解决问题。

## 下一阶段优先级

目标：在维持单服务、SQLite、Skill/API/MCP共用业务约束的前提下，补齐运行器。邮件链路先保持稳定，不再为正常测试增加新传输实体。

### 第一批：可诊断的下一步

- 任务响应提供派生progress/next_actions：阶段、责任方、阻塞原因、读取时刻、事件位置。不是第二套持久订单状态。
- 本地运行器报告阶段、PID/存活情况、最后成功同步、下一次重试、累计期限及具体错误。模型402、鉴权失败、网络失败、等待对方分别标识；未收到客户端报告时标unknown/offline，服务端不能自行知道模型账户余额。
- 当前部署版本、发布版本、已验证与待验证项目在README/Release中分别说明。

### 第二批：检测后真正衔接

- 提供单实例、有检查点的watch/run。发现事件后，必须执行已授权的确定性动作，或向宿主可靠提交一次待办并等待处理确认；不能只写文件就退出且声称自动推进。
- 处理游标、幂等键、原始请求体和步骤结果持久化；重启先读取当前任务，不重复报价、选中、确认、发信或验收。
- 动作执行仍受用户预算、指定供给方、收件人和文件范围约束；LLM需要决策时按宿主能力唤醒，不授予脚本无限采购或验收权限。
- 完成、超时、明确故障及用户停止后可退出；新指令不启动第二份进程。发信不确定保留对账流程，不盲目重发。

### 第三批：V05运行可靠性验证

新订单验证不同上线顺序、select后唤醒、进程重启/重复启动、重复提示、用户停止，以及受控模型不可用时明确报告并恢复。正常配置下从发现到确认不依赖人工转话；故障人工恢复与正常自动运行分别计数。
