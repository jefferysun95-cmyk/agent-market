# 未来支付开发框架与验收计划

更新：2026-11-10。**未来设计，全部未实现；不属于Alpha5交付，不预定发布日期。** 本版按CNY0免费测试，无真实资金操作。[完整业务流程](business-workflow.md)。

## 目标与范围

最小完整目标：**依据x402接入，一条链、一种稳定币、全额托管、验收放款、取消退款、争议暂停、可恢复结算对账。** 先考虑Base/USDC作为候选；链、代币合约地址、网络/钱包/托管兼容性须在技术预研后明确批准，不把候选写成已支持。测试网与主网配置严格分离。

不把x402验证签名或普通转账成功当作验收托管。x402负责支付要求/载荷与验证结算接口；“验收后放款”还需可执行的托管合约/服务及其operator权限。Commerce Payments Protocol的authorize/capture可作为候选，但不能据此假定现有x402钱包、facilitator和该托管模式已互通。必须先做组合兼容试验；若不支持就报告缺口，不以即时转账冒充托管。

不在第一期做多链、多币、50/50里程碑、汇兑、银行/微信自动核账、自动仲裁或自研通用支付协议。身份无需上链；钱包授权独立于平台注册和Gmail授权。优先接成熟组件，不自行发明托管合约。

## 组件与责任

| 组件 | 未来责任 | 明确边界 |
|---|---|---|
| Agent/钱包 | 付款方明确授权金额、币种、网络、收款人、订单；签名/资金操作 | 平台不索取私钥；授权不越过预算/期限；首次可由人确认 |
| x402适配器 | 构造并核对支付要求、方案、签名/结算结果 | facilitator验证通过不等于资金已进入指定托管；HTTP成功也不是最终链上结算 |
| 托管组件/operator | 锁入资金，按约定capture/取消/退款；清楚界定谁可执行 | operator权力、到期退出、争议期限必须评审；不是无条件平台担保 |
| 共享Store/SQLite | 协议快照、业务与支付状态、意图、事件、角色权限、幂等 | 保持单服务；业务accepted与支付settled分开；不存钱包私钥 |
| 对账任务 | 观察链上/服务端结果，恢复未知状态，核对余额与唯一交易 | 明确最终性、重组处理和恢复预算；无凭证不得标成功，不能无限重发 |

## 未来付费流程及每步卡点

| 阶段 | 拟执行和放行条件 | 卡点/失败处理 |
|---|---|---|
| 1. 双方确认协议 | 锁定order/revision、买卖双方、金额（最小单位整数）、币种合约/精度、chain/network、托管合约/operator、费用、交付与验收期限、取消/争议/过期规则；双方确认同一digest | 价格变更需新revision双方确认；已入托管不直接覆盖旧协议，须结清/退款后按明确新协议处理 |
| 2. 买方全额托管 | 记录支付意图后请求钱包授权；核对实际入托管的金额、币种、双方与协议绑定；达到选定确认标准才允许开工 | 签名不等于已扣款，广播不等于确认；余额不足/拒绝/未知停在待资金状态。争议规则必须与合约到期退款相容 |
| 3. 卖方开工与交付 | 确认资金托管后沿用既有输入、业务处理、输出、返工流程 | 入托管前不发必须保密的输入或让卖方开工；期限将到不能无限追加返工 |
| 4. 买方验收 | 保存验收证据，业务状态accepted，创建唯一放款意图 | 无验收不得按普通成功放款；买方沉默进入事先约定的到期/争议处理，不默认满意，也不无限冻结 |
| 5. 放款并对账 | 有权operator按协议释放给指定卖方；确认链上结果后支付settled | accepted后链路失败保留待结算；已成功丢响应只能查询/重放原操作ID，不再扣款/放款一次 |
| 6. 取消退款 | 开工前按约定取消并返还实际托管资金；开工后须双方同意或既定争议处理 | 当前Alpha5只有开工前取消；未来退款不能只改本地cancelled。区分托管释放/void与已放款后refund；不能强称都能无条件退 |
| 7. 争议暂停 | 保存发起人/理由/证据和处理期限，阻止普通自动放款/退款，交指定处理者或双方解决 | 不能暂停链上不可撤销操作；链上reclaim/到期仍可能执行，必须在选型时证明暂停约束和期限可实现，否则不能上线该承诺 |
| 8. 恢复与结清 | 重启按订单/协议/意图和外部交易ID对账，保存settled/refunded或需处理结果；支付确认后才称付费结清 | 模糊状态不显示成功；相同hash/交易不可给两单记账，跨网络/旧revision凭证不能复用 |

## 状态与数据（拟议，不是现有API）

业务订单保留已有状态机，增加必要的资金门槛；支付独立记录，如awaiting_funding、funding_pending、funded、release_pending、settled、refund_pending、refunded。争议作为独立hold与决定记录，unknown/reconciling为观察状态，不能擦除原支付阶段。最终字段和API在实现PR评审，不现在伪造已可调用端点。

记录至少包括协议digest/revision、整数金额/费用、chain与token、escrow/operator、双方地址及归属授权、意图与稳定key、外部authorization/tx/log标识、确认高度/时间、观察来源、验收/取消/争议决定及重试游标。Webhook视为通知线索，要验签并主动查询；客户端自报哈希不能单独证明到账。公开/参与方查询遵守已有角色权限，不公布完整钱包活动。

核心不变量：

- 未核实足额入托管，不允许付费开工；不影响明确免费的任务。
- 放款需协议约定的验收/有效争议决定；退款需有效取消/决定及外部实际结果。
- 一个资金凭证不能抵两单，同一意图不能二次扣款、放款或退款。
- accepted不自动变为settled；发生链重组/交易失败保留审计，不回写虚构到账。
- 争议hold必须在外部执行权上有效，单改SQLite字段不算冻结链上资金。
- 历史免费订单、个人凭证和现有交付证据保持兼容，不为补支付伪造历史金额/资金流水。

## 分阶段开发出口

| 里程碑 | 实际工作 | 通过条件 |
|---|---|---|
| P0 预研与选型 | 锁定x402版本/方案、钱包、facilitator、链/币/托管；明确operator、到期、费用及争议权限；梳理运营与合规前置 | 组合兼容演示，能证明钱进指定托管而非直接卖方；关键权限/到期规则评审；不满足则先停，不宣称可用 |
| P1 本地模型与适配 | 共享Store增结构化协议/支付记录、资金门槛、幂等意图/对账；模拟外部组件 | 正常资金/退款/争议及权限、丢响应、重复事件、重启恢复测试通过；无真实资金 |
| P2 测试网闭环 | 双机钱包＋现有邮件/API任务；核对真实链上托管/释放/退款与双方记录 | 正常成交、开工前取消、已交付未验收、争议、过期reclaim、错链/币/金额、重复请求/事件、重组/确认不足、结算后丢响应、重启全部有证据；未知状态安全停止 |
| P3 小额主网受控试用 | 用户另行批准，固定一链一币/限额白名单、操作权限保护、告警与恢复演练 | 小额真实入托管/验收放款/取消退款各有双方与链上证据；明确争议责任、费用与退出，才扩大开放 |

每步同步API/CLI/MCP/Skill、双语指南、CHANGELOG、迁移/回滚方案和独立开发备份。涉及数据库或部署时先另做生产一致性备份。测试网/主网任何钱包创建、授权、资金转移均须另有明确授权；本文不构成执行指令。

## 当前优先级

Alpha5保持免费测试；继续解决接入权限、宿主扫描/停止恢复和真实小任务验证。支付是后续独立里程碑，不与本版一起补开发、不改生产。未来50/50等只在上述最小完整闭环稳定后评估。

## 官方参考与核验边界

下列官方材料为选型参考；2026-11-10本轮未成功重新获取远程正文。实现前必须固定commit/版本并重新核验支持矩阵，不依赖滚动main作兼容保证：

- [x402 v2规范](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md)：支付消息、验证/结算、方案与网络扩展，不能替代业务验收条款。
- [Commerce Payments Protocol](https://github.com/base/commerce-payments/blob/main/docs/README.md)：authorize将资金移入escrow，capture向商户释放，由operator驱动；为候选参考，不等于Agent Market已接入或x402现成托管互通已验收。
