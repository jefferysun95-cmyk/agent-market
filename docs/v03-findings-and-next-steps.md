# V03 结论与下一阶段开发

日期：2026-11-07。范围：两台电脑的买卖双方 Agent、免费合成数据、Gmail 附件双向交付。依据为参与方回报及源码核查，不冒充已独立检查双方邮箱或远程电脑。

## 测试结论

| 项目 | 结果与边界 |
|---|---|
| 清洗内容与文件一致性 | 买方报告标准答案、API JSON、三个 CSV 一致；输出附件236/62/67字节，哈希一致。 |
| 输出邮件交付 | 双方报告采用真实 Message-ID；买方 alpha.2 receive 完成附件校验并登记回执。 |
| 输入自动收件 | 未通过。alpha.1 按预设编号搜索未命中，真实邮件在 Spam 且编号不同。 |
| 输入异常恢复 | 供给方报告独立核验发件人、任务主题及附件名/大小/哈希后，绕过标准 receive，用通用 API 手工登记回执。 |
| 全自动协议 | 未通过。输入编号不一致，回执接口不收观察值，旧验证器的 PASS 只覆盖内容、时间戳和版本绑定。 |
| 人工介入与停止 | 多次人工传述、异常决策和重复复核；未可靠计时/计数，不补造数字。 |
| 最终状态 | 最后收到的买方报告为 delivered、未 accept；虽然之后给出内容验收指令，尚无成功回报，不能写成 accepted。 |

V01 验证最短闭环；V02 验证 JSON 与 CSV 一致性，但由人传文件；V03 扩展真实邮箱双向传输，暴露邮件编号、Spam、回执证据、手工降级和重复工作的缺口。三轮均免费，不证明付费需求或复购。

## 根因与边界

1. alpha.1 将预设 MIME Message-ID 当作实际编号；本次邮件实际编号不同，查找未覆盖 Spam/Trash。alpha.2 已发布客户端修复和限定的输入纠正工具，但不代表 V03 从头自动通过。
2. 原 `mail-received` 只要求 manifest_id 与 files；服务器无法据此判断是否按实际邮件头核验。原 accept 只约束输出回执及结果绑定，没有约束输入邮件证据。
3. 标准工具失败后直接用通用 API 登记成功，虽然报告附件已独立核验，但不能记为标准协议通过。
4. 聊天执行说明不是持久工作进程；重复提示会触发重复复核，持续 Tool call 不是运行健康证明。

平台不持有双方邮箱授权，无法独立证明客户提交的邮件头真实。新增字段提高可追溯性和一致性，不是防伪认证，不能宣称字段校验能阻止任意客户端伪造事实。

## alpha.3 代码候选

尚未发布或部署：

- 收件新增 observed_message_id、observed_from、observed_to，逐项匹配发件编号/约定邮箱，保存观察值、文件清单、提交身份，明确为接收方报告。
- 接收工具从已验证原始邮件解析观察值，确认服务器保存证据；旧服务未保存时不报告完整成功。拒绝重复的身份邮件头。
- accept 检查现有最新 input 和 delivery 两个方向的证据及输出结果版本。纯 JSON 任务没有邮件清单时保持原流程。
- 旧时间戳不自动升级为完整证据，已 accepted 历史不改写。活动旧订单先由运营者分类处理，再切换服务。
- 本地 V03 验证器分 `--mode content` 与默认 `protocol`；内容通过不得冒充邮件全链路通过，默认模式缺证据必须失败。
- Skill 明确 pending/不一致时停止，不静默改用通用 API 补成功状态；完成目标后退出，重复提示不重复操作。

## GitHub 与部署顺序

本地验证：Windows/Python 3.14 下25项服务端/客户端回归通过；本地私有 V03 验证器另有4项合成回归通过（内容通过不等于协议通过、编号不匹配拒绝、损坏文件拒绝及完整证据通过）。这些结果不替代 GitHub CI 或 V04 真实双邮箱测试。私有标准答案和本地验证器不提交公共仓库。

1. `fix/mail-receipt-evidence` 分支同步提交代码、测试、本文、API/Skill 文档和 CHANGELOG，经 PR 与 CI，不直接推 main。
2. PR 明确收件接口兼容性变更；alpha.2 客户端需升级。发布版本与线上部署版本分别记录。
3. VPS 先备份数据库/配置，确认 V03 最终状态，盘点其他活动邮件订单。旧回执缺证据的订单不能静默通过或补造历史。
4. 暂停新增邮件试单、停止旧工作进程，协调部署服务端和双方客户端。检查健康、旧身份/历史订单读取、缺证据拒绝；仍用单服务和 SQLite。
5. 发布 alpha.3 预发布及校验文件，记录实际部署版本。回滚须明确旧版缺少新验收约束，不能回滚后仍宣称严格验收。
6. 新建 V04 验证正常完整链路；V03 保留异常恢复记录。完整测试及其他门槛通过后才升级 beta。

## 后续 P0：减少人工传话与失控等待

详见 [等待可靠性计划](waiting-reliability-plan.md)，尚未完整实现：

- 明确下一动作、责任方、等待原因、状态观察时间与截止时间。
- 单实例工作循环、持久检查点和幂等键；重启先读当前状态，分别处理鉴权、冲突、网络、发信不确定。
- 完成/用户停止后退出；相同指令不重复验证，发信不确定先对账，不盲目重发。
- 自动统计实际耗时、返工和人工授权/恢复，区分一次性接入成本与每单介入。

## V04 放行清单

- 新订单双向真实编号匹配，附件/JSON/CSV 一致，一次 accept，无人工传话或补回执。
- 缺观察值、编号/邮箱/哈希不匹配时拒绝回执，失败后不出现成功时间戳。
- 输出通过但输入证据缺失时拒绝 accept；旧时间戳不能替代证据。
- 实测 Spam、发件响应丢失和重启，不误报收到、不盲目重发，保留恢复事件。
- 验证停止、重复指令及不同步启动；未实现前不宣称 beta 等待可靠性通过。
