## 启动前门槛

1. 两台电脑安装同一冻结候选 commit/源码或 wheel，SHA256 一致，版本兼容实际服务器；不覆盖原 alpha.4 安装和私密凭证。
2. 各端只读 `/health`、`/me`、Gmail profile；核对角色与邮箱。缺配置在发布前解决，不再重复注册/授权或搜索整块磁盘。
3. 两端真实 OpenClaw 只读预检通过，运行模式、内部 agent ID、工具权限及工作目录均记录；不能只用固定脚本回 ready。
4. buyer/supplier 的 supervisor、子工作登记、pending 再调度、stop/resume、错误分类和验收处理器均已实现且本地回归通过。只有 generic host/pull-ack 不够。
5. 两端时钟/时区可核对，日志统一 UTC；总耗时按服务端事件计算，本地执行时长使用单调时钟。时钟异常须先阻塞，不凭聊天时刻估算。
6. 固定输入只在买方；供给方包含规则/契约/工具，不含实际输入数组或私有答案。身份凭证、邮箱授权和生产数据库均不进入测试包或 Git。

全部 readiness 通过后才允许创建 V05 新单；不得复用或修改 V01–V04、A4-MAIL-01 历史 accepted 订单。

## 数据与交付

使用新生成的约 12–20 条文具订单；不同正常用例使用不同 run_id、订单号和输入字节。包含重复订单（有冲突与无冲突）、合法/非法闰日、非法日历日期、歧义日期、空日期、中文/逗号/引号/字段内换行。

冻结规则：source_row 从 1 起，按 order_id 保留首次整条记录并保序；quantity 为样本已合法的整数，note 原样保留；严格接受有效 `YYYY-MM-DD` 或 `YYYY/MM/DD`（斜杠转横杠），歧义或非法日期保留原串并标 date_error=true；空日期单列 MISSING_DATE，其余 INVALID_DATE。先去重，再计算异常。

API result 为 rows/exceptions/duplicates/summary；CSV 为 cleaned_orders.csv、exceptions.csv、duplicates.csv，UTF-8、明确列顺序、布尔小写、正确引用换行/引号。具体 schema 与规则 JSON 同时冻结并以哈希确认，拼写/日期格式以该冻结机器契约为准。

测试包生成时在买方计算私有标准答案和期望摘要；供给方不获得答案。输入仅通过真实邮件附件取得。验收同时比较原始附件字节/哈希、CSV 解析后的逻辑记录与 API JSON，不以物理行数比较 CSV。

## 两个必须通过的正常用例

| 用例 | 启动顺序 | 自动化要证明什么 |
|---|---|---|
| V05-N1 | Quincey 先运行待发现；AngelX 后启动并发布 | 供方能发现新需求，买方处理新报价，后续确认/邮件/验收不断链 |
| V05-N2 | AngelX 先发布；Quincey 约 60 秒后启动 | 供方补查已存在需求，不只等未来通知；买方不会因早期空列表永久等待 |

每端只启动一次。维护者只观察，不给供给方任务号。各端通过 run_id 白名单、类别、actor 及当前真实 task_id 关联；标题只作为辅助显示，不能只匹配 V05 字符串。

完整路径：自动发现/报价 → 自动比较选择 → 双方各自自动登记邮箱 → confirm → 输入 manifest/真实发送 → 收取并保存实际证据 → 真实 OpenClaw 处理 → 输出 manifest/真实发送 → deliver → 买方收件及私有验证 → accept → 双方终止该单。deliver 不等买方回执，accepted 不等供给方再次确认。

初始建议期限：总计 30 分钟，报价/选择与确认各 5 分钟，单向邮件 pending 3 分钟，模型回合 120 秒/最多 2 次；最终以同一份冻结策略为准。超时要有明确责任方和原因，不无限续轮询。

## 故障与恢复矩阵（与正常通过分开）

| 用例 | 注入点/方式 | 必须观察到的结果 |
|---|---|---|
| R1 | 发现前/有待办时重复启动同一身份 | 第二实例拒绝；无重复报价或独立轮询 |
| R2 | 模型结果已写但尚未 ack 时结束受管工作，再恢复 | 绑定一致时复用候选；无重复业务动作，不把旧结果用于新 revision |
| R3 | API 写入成功但响应丢失 | 重读或原 key/body 重放，业务效果仅一次；不另造 key |
| R4 | 普通等待中 stop，再明确 resume | 全部已登记子工作停止，保留原到期，不杀其他 OpenClaw 会话；恢复后安全继续 |
| R5 | 模型不可用/402、平台 401/403/409、邮箱失效、短暂断网 | 来源分类正确，有限重试/退出；UI/状态不假在线，不把模型错误归因平台 |
| R6 | 邮件发送结果不确定、发送或收件回执响应丢失 | 使用原 outbox、实际 Sent/原清单对账；无盲目重发、替换清单或补造头 |
| R7 | 错误附件哈希/错误观察值/旧 manifest 或 revision、未知宿主 JSON、伪 work_id | 不登记 verified，不 accept，不执行未经授权的写入 |
| R8 | 邮件进入 Spam/Trash 或 Gmail 改写 Message-ID | 记录实际邮件头并正确收件；不把合成编号当实际编号 |

先在临时服务/模拟邮箱完成可控故障，再对批准的 V05 专用新任务执行受控真实进程停止/恢复。不能为了造 401/409 等故障修改现有真实凭证或历史业务数据。若本轮没有自然出现 Spam，模拟覆盖与真实观察分别记录；不得为了造 Spam 扩大 Gmail 权限或操作无关邮件。无法安全注入的真实模型 402 等情况标“模拟验证/真实未观察”，不冒称真实通过。

## 证据、指标与判定

每单保存本机原始 API 快照/事件、双方 supervisor 与宿主工作摘要、输入/输出清单、观察回执、实际附件、私有验证结果和人工介入日志。只存必要摘要，不把密钥、原始邮箱授权或私有答案提交 Git。

独立报告三个维度：

1. 内容：私有 JSON、CSV、字节和哈希一致。
2. 传输：双向实际 Message-ID/from/to/files/actor 与最新版本绑定，未手工补回执；证据仍为参与方报告，independently_certified=false。
3. 编排：N1/N2 在启动后无人工传话/传号/传文件/唤醒，双方自行到 accepted 且停止；有额外人工动作即编排不通过。

记录发布→报价→选择→confirm→输入收件→首次交付→输出收件→accept 的服务端时间、模型回合次数/实际耗时（若有）、API/邮件重试、重发、返工、重复业务效果、停止延迟和人工次数/分钟。未知标未知，不补 0。空闲等待不得产生模型回合；各进程状态必须与 OS 存活和最近同步对应。

内容通过但编排失败：可以保留真实 accepted 结果，必须标自动化失败；不要再靠人工完成后把这单计入 N1/N2 通过。修复后新建有独立 run_id 的用例，不覆盖原始事件。
